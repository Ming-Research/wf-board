Decision: A second launchd job, apart from the daemon, deploys the main line every five minutes: it fetches through the bounded remote-git function, fast-forwards the daemon's checkout, installs packages when the lock file changed, rebuilds the page, restarts the daemon unless every changed path is one the daemon does not load at its start, judges health by a new process that answers the health route and still answers five seconds later (a deploy that needed no restart waits for the health route alone), resets to the last healthy commit when the daemon does not come up, records a pending deploy before it moves so that a dead run is finished next time, and undoes only what it did to a checkout that is still the one it moved, while it moves a checkout only when that is on the main line with no changes to tracked files (a submodule's own files do not count) and no commit the main line lacks, because the daemon cannot restart itself onto new code and also answer for whether that code runs, and a failing deploy must not depend on the new code to go back ([Deploying](../docs/design.md#4-architecture)), instead of the daemon deploying itself or someone deploying by hand after each merge.

Decision: The deploy job moves the checkout to the main line's head only when GitHub reports every check on that commit passed, read by the function the board's look at the main line reads a commit with, and otherwise leaves everything where it is and asks again on its next run: a head whose checks are running or have not appeared is waited for (and pushed once if still unfinished an hour after the job first found it so), a head with a red check is held without a push of its own, since the look at the main line tells the red, until a newer commit passes or the check passes on a rerun, and checks that cannot be read count as not green and are pushed once, because the full CI that passes before a merge cannot see a break that exists only on the merged main line, such as two pull requests each green and red together, and a bad live board stops every agent and the owner ([Deploying](../docs/design.md#4-architecture)), instead of deploying every merge as soon as it lands, and the head alone decides instead of the newest green commit among those not yet live, because a batch of merges stays one deploy and one restart.

Rejected:
- The daemon restarting itself onto new code: rejected because it cannot also answer for whether that code runs.
- Someone deploying by hand after each merge: rejected because it needs someone present at every merge, a missed merge leaves the live board behind the main line, and nothing goes back by itself.
- Moving or undoing a checkout that is on another branch, has tracked local changes or holds a commit the main line lacks: rejected because that edit or commit belongs to someone, not to the job.
- Recording the daemon's process id in the pending record to close the half-deploy gap: rejected because it was judged not worth the added recovery logic.
- Deploying every merge as soon as it lands: rejected because the main line's own checks, which run after the merge, are the only ones that can see a break that exists only there, and a merge with a red check went live.
- Deploying the newest green commit among those not yet live: rejected because a head whose checks are still running would put an older commit live and the head itself a restart later, and each restart drops every session's stream.
- A branch pointer that the main line's CI moves forward when it passes, which the job fetches instead of asking GitHub: rejected because only the jobs of the workflow that moves it count, so the checks of the other workflows would not, and it needs write permission for the workflow and a guard against runs that end out of order.
