Decision: A second launchd job, apart from the daemon, deploys the main line every five minutes: it fetches through the bounded remote-git function, fast-forwards the daemon's checkout, installs packages when the lock file changed, rebuilds the page, restarts the daemon unless every changed path is one the daemon does not load at its start, judges health by a new process that answers the health route and still answers five seconds later (a deploy that needed no restart waits for the health route alone), resets to the last healthy commit when the daemon does not come up, records a pending deploy before it moves so that a dead run is finished next time, and undoes only what it did to a checkout that is still the one it moved, while it moves a checkout only when that is on the main line with no changes to tracked files (a submodule's own files do not count) and no commit the main line lacks, because the daemon cannot restart itself onto new code and also answer for whether that code runs, and a failing deploy must not depend on the new code to go back ([Deploying](../docs/design.md#4-architecture)), instead of the daemon deploying itself or someone deploying by hand after each merge.

Rejected:
- The daemon restarting itself onto new code: rejected because it cannot also answer for whether that code runs.
- Someone deploying by hand after each merge: rejected because it needs someone present at every merge, a missed merge leaves the live board behind the main line, and nothing goes back by itself.
- Moving or undoing a checkout that is on another branch, has tracked local changes or holds a commit the main line lacks: rejected because that edit or commit belongs to someone, not to the job.
- Recording the daemon's process id in the pending record to close the half-deploy gap: rejected because it was judged not worth the added recovery logic.
