Decision: The board's data is a git working tree of plain files beside the checkout, and each logical operation is one commit authored by the writing project (or by the owner) whose message summarizes the operation, because every change is then kept with who made it and when, and an agent can still read the files with ordinary tools while the daemon is down ([Storage](../docs/design.md#4-architecture)), instead of a database, which would hide the data from everyone but the daemon.

Decision: A write commits exactly the paths it wrote (`git commit --only`) and does not look at the index first, so a file staged by hand neither enters the board's commit nor stops the write, and a staged or changed board document is still refused at the next start unless a board write to that document came first, which commits the board's own version over the hand edit, because only the daemon writes the data directory, so a staged file there is outside the board's own working and the start already refuses uncommitted board documents, while the look at the index cost every write a git process, about 5 ms of the daemon's CPU in a profile on a hosted runner taken while the daemon held about 1.9 GB, before its leak was fixed ([Write cost](../docs/design.md#4-architecture)), instead of refusing every write while anything is staged.

Decision: The board runs the data repository's maintenance itself, as a task of its write queue after every 100 commits, and turns git's own off (`gc.auto=0` and `maintenance.auto=false` on every git command that writes the repository), with a backlog found at open maintained before the daemon listens and no new step queued once the shutdown has begun, because a step then follows one constant and never overlaps a write: git's repack, started after a commit at a time and in a size the board does not choose, held a write for 5.7 seconds on the live repository against the three seconds a write may wait, and left in the background deleted an empty object directory while the next `git add` created a temporary file in it ([Maintenance](../docs/design.md#4-architecture)), instead of leaving the repack to git.

Decision: A step covers 100 commits, because on a hosted runner, replaying the live board's busiest ten minutes against a copy of its shape, such a step took at most 753 milliseconds (median 240 to 299) where 200 commits took up to 1,699, and converted to the live Mac, which may be 1.45 times slower, 100 stays under the two-second line at which a slow write is told to the architect and 200 reaches it, instead of 200 or 300 commits; the number is provisional until the service log of the live board confirms it ([Maintenance](../docs/design.md#4-architecture)).

Decision: A step packs the loose objects into one pack, writes a commit-graph, and, when the repository had more than 8 packs before it, merges the small packs in batches of about 16 MB with the multi-pack-index, because every step then has a bound that does not grow with the repository (at most 906 milliseconds over 12,000 synthetic commits, at most 10 packs) and a history query is about 6 times faster with the commit-graph, at the price of about four times the disk per commit, instead of git's geometric repack ([Maintenance](../docs/design.md#4-architecture)).

Decision: Every document is a YAML file with prose in literal blocks (one file for each document, except that messages share one file for each UTC day and the tag vocabulary shares the board file with the project list), written only by the daemon through one serializer and checked against a schema on read and write, because a git diff then shows the changed lines of prose and plain tools show readable text while the structure stays exact ([Data format](../docs/design.md#5-data-format)), instead of JSON or Markdown with front matter.

Decision: Every YAML document the board reads goes through one function that parses it and then copies the result with `structuredClone`, so that each string is flat and holds nothing of its source text, and the history cache weighs a parsed document at 2 bytes of heap for each byte of its file, because the library's strings are slices that keep the whole source text alive (two bytes a character for Chinese) or are joined one character at a time (about 32 bytes a character until something reads the string), and the board never reads most of the strings it holds: opening the real store on a synthetic board in the live board's shape (21.8 MB of files) kept 62.3 and 66.9 MB of heap in two runs and 27.0 MB with the copy, and on a board whose long texts are single-line quoted scalars 604.9 MB and 29.2 MB, for 83 to 123 ms more on a parse of about 2.5 seconds, and the flat documents measured 1.2 to 1.5 times their files ([Parsed documents](../docs/design.md#4-architecture)), instead of keeping the library's result as it is and weighing it at 16 bytes of heap for each byte of file, a figure measured on the quoted-scalar board.

Decision: Each fact is stored once and places are derived: a card's place is its item field alone, an item's place is the one plan row that owns it, a note's title comes from its target, and an item's project is stored once and changes only together with everything the item owns, so that the stored field and the ownership chain always agree, because the copies of a relation stored on both sides went stale in the board's earlier form (27 cards missing from their item's list, 572 items holding both a parent and an area, 13 stale note titles), instead of storing a relation on both sides.

Rejected:
- Refusing every write while anything is staged (the first version): rejected because it costs a git process per write for a state only a hand edit of the daemon's own directory makes, which the start already refuses for board documents.
- Looking at the index in the repository maintenance every 100 commits and telling the architect of a staged or changed board document: rejected because a hand edit of the data directory has not happened, so the earlier notice would guard nothing yet, at the price of one more push and its tests.
- A database: rejected because the data would be hidden from every tool but the daemon while it is down.
- Detached background maintenance: rejected because a git process would then write the repository outside the write queue.
- Git's automatic maintenance in the foreground of the commit that triggers it (the first version): rejected because the first repack on the live repository held a write for 5.7 seconds, over the three-second line, and its size grows with the commits waiting.
- Maintaining when the board is idle, only at start, or at fixed times: rejected because the busiest ten minutes of the live board leave no idle time to rely on, a start-only step has no bound on the backlog, and a step at fixed times grows with the writes.
- Git's geometric repack for each step: rejected because every few thousand commits it rewrites the whole repository in 3.6 to 4.4 seconds, over the line and growing with the repository.
- Packing without merging the small packs: rejected because the pack count has no bound (63 after 60 steps).
- A smaller disk for the board's data by a `.keep` file on the large packs: rejected because every step then took 2.2 to 2.6 seconds, since each pack kept out must be registered as a source of deltas.
- JSON files: rejected because a paragraph becomes one escaped line, so a one-word edit rewrites the whole line in a diff and plain tools show escaped text.
- Markdown files with front matter: rejected because structure inside the body, such as a log entry's time and author, needs reserved heading lines, and every new field would stretch that encoding.
- Storing a relation on both sides (item lists on cards, a parent beside an area, stored note titles): rejected because the copies went stale.
- Rebuilding each string of a parsed document in place, or a round trip through JSON: rejected because both cost more time than the copy on the whole board (129 to 545 ms and 102 to 151 ms against 83 to 123 ms).
- Parsing once and keeping a JSON startup cache of the validated documents: rejected because it adds a second copy of the data, as large as the board, and a new way to start wrong, a cache that differs from the working tree, while a start of 3.3 seconds already meets the 5 seconds the restart item set; it can be added later and does not conflict with the copy.
- Replacing the YAML library with js-yaml: rejected because it parses 5 times faster (465 ms against 2,508 ms) but its result keeps about the same heap (54.5 MB against 57.7 MB), so the copy is needed anyway, and it changes the dependency, with the library's YAML 1.2 details untried on the live data and the writer still the old library.
- Changing only the history cache's weight: rejected because no heap is released: the store keeps about 35 MB it does not use, and a long double-quoted text still keeps about 41 bytes a character.
