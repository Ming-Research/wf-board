Decision: The service starts the daemon with two V8 flags in its service file, `--max-semi-space-size=4` (each half of the young generation at most 4 MB) and `--heap-growing-percent=50` (a full collection once the old generation reaches 1.5 times what survived the last), because on a macOS hosted runner with the live board's shape and request mix they cut the V8 pages the process holds, the largest part of its physical footprint, from 584 MB to 269 MB for 5% more CPU a request and the same latency ([Memory beyond the heap](../../docs/design.md#4-architecture)), instead of node's defaults, which let the young generation grow to 128 MB and the old one average 2.7 times its live data between full collections.

Rejected:
- `--optimize-for-size`: rejected because it cuts the pages further (118 MB) but doubles the CPU a request (34.4 ms against 18.2) and collects the whole heap about 13 times as often (920 times against 72 in the same eight minutes), a cost an always-open board would pay for a further 150 MB.
- Only `--max-semi-space-size=4`: rejected because the old generation still averages about 2.7 times its live data, so the pages stay at 375 MB.
- `--max-old-space-size=512`: rejected because it lowers the heap limit that the request budgets set their lines by (section 4, Request budgets), where the growing percentage changes only when the heap is collected.
- Setting the flags from the code after the process has started (`v8.setFlagsFromString`): rejected because the semi-space size is fixed when the process starts, so the flag does nothing (the start log's rss stays at 329 MB against 224), and the growing percentage alone cuts the pages by only 28%.
- `--memory-saver-mode` and `--memory-balancer`: rejected because they cost as much CPU as `--optimize-for-size` (38 and 41 ms a request) without its saving.
