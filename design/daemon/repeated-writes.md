Decision: A write that only adds a line (a log entry, the closing of an owner note, a status change, a journal entry) is not made again when the item's history already holds, from the last minute, a commit of the same operation on the same target by the same session that left the item holding that line (for a status change, only while the item is in the state the call asks for), and the answer is that first commit marked as repeated, found from the history with nothing kept in memory so that it holds across a restart, because a client resends a write that was committed but not answered when the board stopped, and these four writes have no other check that stops a second copy ([MCP without a session](../../docs/design.md#4-architecture)), instead of letting a resent write add its line twice; a caller that names no session is not recognised and writes, and when the request's history budget is spent the write is made, at worst once too often.

Rejected:
- Letting a resent write add its line twice: rejected because none of the four writes is refused or a no-op when repeated, unlike the other writes (a used key, a stale revision, an unchanged plan, a note already replied, an ended dispatch).
