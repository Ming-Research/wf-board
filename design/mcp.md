Decision: Every tool returns compact text, and the two reads that returned the most, `context` and `overview`, answer with a summary by default (a head section's first paragraph cut at a limit, finished rows folded, option grounds left out, handled notes and long logs cut) where every cut says how much it left out and which parameter returns the rest, because a reply stays in the caller's context until it is compacted (433 `context` calls returned 1.59 million characters, and one `overview` answer cost 24 thousand characters) ([Lean replies](../docs/design.md#lean-replies)), instead of the whole answer by default. This is a temporary trim, reopened when the planned redesign of the tools is made.

Decision: A write refuses a head that holds the exact marker line of a cut answer and says to read the whole head first, because a head copied from a cut answer would silently drop the text the answer left out.

Decision: The MCP server's instructions are a short pointer, of at most 2048 characters, to the board section of the shared agent rules, with three first steps and no rule of their own, because Claude Code cuts longer instructions at 2048 characters (observed) and the owner decided that the rules for using the board must stay in the agent's context for the whole session, which the shared rules do, and a rule the server enforces is defined once in the model or rules module ([Server instructions](../docs/design.md#server-instructions)), instead of the full rules in the server's instructions or a guide tool.

Decision: `update_item` changes a head in parts as well as whole, by `sections` (whole sections replaced by title) and `replace` (texts replaced, each found in the head exactly once), where every edit is located in the head as it is before the call and no two may change the same text, so the order they are written in changes nothing, all are made in one commit or none and the first that does not fit refuses the call and is named, a revision that is behind stands when the head did not change since as for a whole head, and the answer shows each change as the lines before and after it, because a change of a sentence cost a read and a resend of the whole head (583 whole-head rewrites in eleven architect sessions, and an exact-replace script of the architect's own run more than a hundred times, 75 changes to seven rule blocks in one day), and a text that must occur exactly once is a guard that a misread or outdated edit cannot pass silently ([Changing things](../docs/design.md#changing-things)), instead of a tool of its own, a patch text or whole-head writes only.

Rejected:
- The whole answer by default (the previous behavior): rejected because of its measured cost in the caller's context.
- Accepting a head written back from a cut answer: rejected because it would drop the text that the cut left out.
- The full rules in the server's instructions: rejected because they would be cut at 2048 characters and reach no agent.
- A guide tool or resource for the rules: rejected because it adds a call the agent must make and does not keep the rules in its context.
- A tool of its own for changing a head in parts: rejected because the reason, the revision rule, the log line and the check for a cut answer would be wired in a second place beside the head write, and the redesign of the tools aims at fewer tools, not more.
- A patch text (unified diff) as the way to change part of a head: rejected because the writer must supply line numbers and context that are easily a line off, and one hunk that does not apply cannot be named the way an edit in a list is.
- Only texts replaced, with whole sections left to the storing of heads by section: rejected because rewriting a section would still send the whole head back and forth, and both forms share the locating, the overlap check and the answer.
- Replacing the texts one after another, each in the result of the one before: rejected because the outcome would depend on the order they are written in and a text could be found in what an earlier edit wrote.
