Decision: The push to the remote copy runs beside the write queue and no write waits for the network: a push sends the head commit as of its start over one connection, a refusal is followed by one fetch that tells a remote that is ahead from one that has diverged, and every git command that reaches a remote (the store's push and the deploy job's fetch, nothing else) runs through one function that starts git in a process group of its own with automatic maintenance off and ends it, ssh included, after a cap, because a push held inside the queue held every write for seconds and never ended with the network down, while writes have a two-second limit ([Pushing and the write queue](../../docs/design.md#4-architecture)), instead of pushing as a task of the write queue; pushes start 60 seconds after the daemon listens and then come at most every ten minutes, and the five-minute cap and the 60-second delay are provisional, because the cap is deduced from the size of a catch-up and not measured on the real uplink and nothing measured favors another delay, and the cap is reopened when the service log shows a push killed by the cap while it was still sending.

Decision: A remote copy that has lacked commits for an hour is told once to the PM, because a stuck push no longer slows a write, so its only harm is a copy that is out of date without anyone seeing it.

Rejected:
- Pushing as a task of the write queue (the earlier design): rejected because a write made 300 milliseconds into a push waited seconds, and with the network down it never finished.
- Signalling git alone when a command outlives its cap: rejected because ssh is git's child and keeps running when only git is signalled.
- Staying silent about a stale remote copy: rejected because with the push outside the queue a stuck push would otherwise leave the backup out of date unseen.
