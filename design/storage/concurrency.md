Decision: A write that replaces text names the revision it read, stands when that is the current revision or when none of the fields it replaces has changed since (the answer says what changed meanwhile), and otherwise fails with the changes to those fields in the error, while appends to a log and writes of a whole field (the plan, the targets, the tags, the difficulty, the dispatch records) carry no revision, stamp their times on the server and are retried against the latest item so that unrelated concurrent writes survive, and a whole-field write whose result equals the current state makes no commit, because the agents' main pattern was to read an item, append a line and write the item back with its version (five conflicts and several malformed calls in the transcripts), appends should never conflict, a revision read is needless for a field that is replaced whole, and four of the six refusals of a head rewrite seen in two days of transcripts came from a log line someone else had added, each costing a re-read and a resend of a head of more than ten thousand characters while the field replaced was untouched ([Data format](../../docs/design.md#5-data-format), [Changing things](../../docs/design.md#changing-things)), instead of a revision on every write or a refusal on any change since the revision.

Rejected:
- A revision on every write: rejected because appends would conflict, and a field replaced whole needs no revision read.
- Refusing a text write on any change since its revision: rejected because it refused rewrites whose own field nobody else had changed, four times in six, so the writer re-read and resent a whole text for nothing.
- A second revision that moves only with the text fields: rejected because it needs a new stored field and a migration of every item, and agents would then hold two numbers that mean different things.
- A text write with no revision: rejected because two writers of the same field would overwrite each other unseen.
