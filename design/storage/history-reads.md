Decision: A request that reads the git history costs what the range it asks about costs, never what the length of the history costs, and runs under a budget held in its async context (bytes of history read, whole old boards rebuilt, and the heap staying under three quarters of its limit) that fails that request alone with an error saying how to narrow it, a history read that runs under no budget fails, and the caches of old documents, diffs and the one old board are bounded by the heap they are estimated to hold, because `changes` rebuilt a whole old board for each deleted document (about three seconds and half a gigabyte each on the synthetic board of that study, whose long texts are single-line quoted scalars; 56 MB on one shaped like the live board, and 30 MB once documents are parsed flat) and a range with ten deleted notes ran the heap into its 4 GB limit and killed the process together with every session's connection and the owner's page ([Request budgets](../../docs/design.md#4-architecture)), instead of running history queries in a worker thread or a child process with a memory limit; an allocation that reads no history is not stopped by a budget, which is accepted because a budget costs a few counters and stops what actually grew.

Decision: The newest commits of one item, card or note are answered from a list the store keeps of each such file's newest 100 commits (derived by the start's replay, carried on by every commit and kept in the startup cache), asking git for those commits by name (`git log --no-walk=unsorted <hashes> -- <path>`), and a document with no list is decided without git, because a path-limited walk for a document with fewer than the 20 commits asked for ends only at the first commit of the history, which took 2.26 to 2.36 seconds for a document created at the 17,208th of the 39,042 commits of the live data repository, 1.65 seconds for an id nobody wrote and 2.79 to 3.01 seconds in a first run on an earlier copy that did not come again, against under 10 milliseconds for the same commits named (the same bytes), and 1,938 of its 1,996 item files have their 20th newest commit (or the oldest, when fewer) more than 5,000 commits back ([Request budgets](../../docs/design.md#4-architecture)), instead of walking the history for them.

Decision: The list keeps 100 commits of each file, a count that is provisional, because `history` asks for 20 unless told otherwise and a version conflict asks for one commit for each version the writer is behind, while no measurement says how many commits readers ask for, so a read for more than the list holds goes to git as before and the count reopens if the slow `history` and version-conflict lines of the service log (a read line names neither the document nor the limit) show such reads, each costing the length of the history again, often enough to matter, instead of listing every commit of each file, whose size in the startup cache and in the heap would follow the length of the history.

Rejected:
- A worker thread with a memory limit: rejected because it needs the board inside the thread (85 to 550 milliseconds and 41 MB for each copy), a message protocol for the six readers of history, and a test that no reader stays on the main thread, which is the same test a budget needs.
- A child process: rejected because it costs more than a thread and isolates more than is needed.
- Git's changed-path Bloom filters in the commit-graph: rejected because the walk still passes every commit (in a first run on an earlier copy of the live data repository, 0.75 seconds against 3.17, with 7,695 of 38,881 commits judged possibly changed and 7,689 of those wrongly), so its cost still grows with the history.
- Bounding the walk by the document's revision or creation time: rejected because only a recently created document gains (in that first run, 1,937 of the 1,996 item files had their oldest commit more than 5,000 commits back), and the rest still cost the history.
