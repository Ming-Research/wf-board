Decision: The activity index (the times of content writes, each item's last change, the spans when work was paused, the last session to write each item, each session's last two items and the runner's reports that began each state of an item's work, each at the report's `since`, the moment the work entered the state and not the commit's time, the newest 500 for each item, a cap that is provisional and reopens if a job is seen to pass it) is derived from the git history and no board data file stores it, and a start reads a disposable cache kept in git's own metadata directory only when it parses to exactly the current format, is of an ancestor of the head and, when it is of the head itself, agrees with the documents on whether a pause was ever set, and otherwise rescans the whole history and writes the cache at once, because the history already holds the evidence and a restart must give what live writes gave ([Data format](../../docs/design.md#5-data-format)), instead of a stored activity file or a derivation from the whole history at every start.

Rejected:
- A stored activity file: rejected because everything in it can be derived from the history.
- Deriving the index from the whole history at every start: rejected because the start would grow with the history instead of with the commits since the cache.
- Writing the cache at shutdown: rejected because shutdown must fit the time launchd gives.
- Storing a segment of the state on the item at each runner report: rejected because the item would grow with its reports as a log entry per report would, work finished before the change would have no line without a second path that fills it in from the history, and the past would be stored twice.
- Reading the item file's history for each request for a line: rejected because an item file has hundreds of versions of tens of kilobytes, so one request would read tens of megabytes, and the page could not be told when a line moved.
