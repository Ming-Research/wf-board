Decision: The PM has one push stream where the client keeps the number of the last event and reconnects from it and any call by the PM or the architect answers everything pushed so far, while every other agent has a stream of its own where the board keeps how far the stream was delivered and the client acknowledges an event after it printed it, because an engineer calls the board all the time while it works and would otherwise answer events it never saw ([The wake streams](../docs/design.md#the-wake-streams)), instead of one rule for both, or a receipt for each event that is sent with a tool call, which would resend every unanswered event on each connection and cost a call per event.

Decision: Every push kind, its fields, its recipient and whether a call answers it are one table, the board refuses any other kind or field set, and only an event that one session has to act on is pushed (the owner is told of a blocking card on the page, and format flags are seen by whoever wrote the item), because each push is something one session has to act on, as the PM rules and the engineer rules say, and everything pushed stays in the agent's context until it is compacted ([What is pushed](../docs/design.md#the-wake-streams)), instead of pushing the other checks or a push for each pull request that can merge.

Rejected:
- One rule for the PM's stream and the agents' streams, so that any call answers everything: rejected because an engineer calls the board all the time and would answer events it never saw.
- A receipt for each event, sent with a tool call after handling (the resource agent's earlier design): rejected because every unanswered event would be resent on each connection, reaching the agent's context several times, and each event would cost a call.
- Pushing the checks that are format flags: rejected because whoever wrote the item sees them.
- A push for a pull request that can merge: rejected because an engineer merges its own once its checks pass.
