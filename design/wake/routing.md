Decision: A session holds an item while an engineer dispatch record on the item names it and has not ended, the newest start winning when several are open, and a push meant for the holder of an item goes to that session, because the start script writes the record and the finish ends it, so holding needs no call from the engineer and is never forgotten ([Where a push goes](../../docs/design.md#the-wake-streams)), instead of a claim and release tool that the engineer calls, or inferring the holder from who last wrote an item with a step in progress.

Decision: A deploy result and a red main line go to the session that holds the item whose changes section names the merged pull request, which is read from the commit's title, and when no session holds that item the failed deploy and the red main line go to the PM while a successful deploy goes nowhere, because the engineer that merged must act on the result, instead of every deploy going to the PM to forward or only the engineer of the last commit a deploy carried.

Decision: A card that becomes ruled, whether the owner sent a choice on the page or a session recorded one with `rule_card`, is pushed as `card-ruled` to the session holding the card's item, and when nobody holds it a pick the owner sent on the page goes to the architect and a ruling a session recorded to no one, because a card's plan row stands only in its own item's plan, so the session stopped on the card is the one holding that item, the owner's pick had reached only the architect, who did not forward it, so an engineer stayed stopped for two days after the owner ruled, and a pick that says nothing but its option is written handled by the ruling and no longer pushed as a note, so without this the pick on an item nobody holds would reach no one, while a ruling a session recorded was made by a session that knows it ([A card ruled](../../docs/design.md#the-wake-streams)), instead of the architect forwarding every ruling, pushing it to the PM when nobody holds the item, pushing the owner's note to the holder, or pushing every pick to the architect as well as to the holder.

Decision: A merge row that turns done, whether the look at GitHub marked it or a session did by hand, is pushed as `dep-merged` to the session holding each open, unpaused item that has a shared row on the item, and to the architect for such an item that nobody holds, and an owner's row is not told, because a session that waits on another item's merge goes on at the merge while the item stays open until its later steps are done, so `item-done` comes too late, and the architect starts or hands on the work nobody holds ([A merge a waiter waits on](../../docs/design.md#the-wake-streams)), instead of telling only the sessions that hold an item, telling the PM, telling the owner of the item too, or pushing at `item-done` only.

Rejected:
- A claim and release tool that the engineer calls: rejected because it adds two calls an engineer can forget and a second record that can disagree with the dispatch.
- Inferring the holder from who last wrote an item with a step in progress: rejected because one write by another session points the push at the wrong session.
- Pushing every deploy to the PM to forward: rejected because it hands the PM a message that it can only pass on.
- Telling only the engineer of the last commit of a deploy: rejected because it misses the other commits that the deploy carried.
- The architect forwarding every ruling to the session stopped on the card: rejected because it rests on one session remembering to do it, which is what failed.
- Pushing a ruling to the PM when nobody holds the item: rejected because it hands the PM a message it can only pass on, while a pick nobody's session holds is for the architect to act on.
- Pushing every pick to the architect as well as to the holder: rejected because the architect would get a line it can only pass on while the holder acts, and the table would give one kind two recipients where it gives each kind one route.
- Pushing the owner's note to the holder as well: rejected because every comment and explain request on the item would reach the engineer before the architect has judged it, and the note does not say which option was chosen.
- Telling only the sessions that hold a waiter: rejected because an item nobody holds then waits until the architect's patrol, which finds a wait that has ended only by chance.
- Telling the PM when nobody holds the waiter: rejected because it hands the PM a message that it can only pass on.
- Telling the item that owns the merged item as well: rejected because an owner learns of a part at `item-done`, and an owner that nobody holds would send the architect a line for every merge of every part.
- Pushing at `item-done` only: rejected because the item stays open until its deploy and live check are done, long after the merge the waiter needed.
