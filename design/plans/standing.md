Decision: A standing item is an item with the stored mark `standing: true`, which only the architect sets, which excludes the record mark, and which takes no acceptance step and no difficulty, because the board's rules and its long-term promises are work that is always in force and never completes, while status, the checks that ask for acceptance and a rating, and the need for an engineer all read an item as one that will complete, so that a never-ticked acceptance step made four of ten such items raised the check `only-acceptance-left` and all ten `difficulty-missing`, and one mark that every derivation reads says once what a rule added to each derivation would say several times ([Standing items](../../docs/design.md#standing-items)), instead of an acceptance step that is never ticked, a record, a tag the checks skip or a flag on a plan row.

Decision: A standing item is cancelled when cancelled, paused when it or an owner in its project's chain is paused, and otherwise in progress, whatever its plan rows say, its rows for other standing items are resolved and left out of the counts, and no row of an ordinary item may own or share a standing item (refused when the write introduces it), because a status read from rows would make a promise in force look blocked, idle or done, and a row can wait only for what can finish, so a row waiting for a standing item can never be resolved and is to be removed ([Standing items](../../docs/design.md#standing-items)), instead of reading its rows or counting such a row as a dependency.

Decision: An unpaused standing item is needed like any open root and passes the need to the items it owns, so those stay startable and rated, while it is never startable itself, and the whole view lists it only when the runner or an engineer session is on it, because the items under a rule block are real work an engineer can start, while the block is a promise in force and not work waiting for someone ([Standing items](../../docs/design.md#standing-items)), instead of cutting the need at the standing item or listing it as work nobody tends.

Rejected:
- A never-ticked acceptance step: rejected because every other row done makes the board raise `only-acceptance-left`, and each such step adds one more check that reports falsely.
- Turning the rule blocks into records: rejected because a record has no work status and so cannot show the in-progress state the owner asked for, and the work under a record counts as backlog and does not start.
- A tag the checks skip: rejected because status is derived and a tag cannot say always in progress, and the rules would read a name in the tag vocabulary that the owner may rename.
- A flag on a plan row marking it long-running: rejected because it covers only status and the check `stalled`, leaves `only-acceptance-left` and `difficulty-missing` in place, and lets anyone set it to hide a check.
