Decision: The deploy job keeps the daemon's installed service file equal to what the template of the commit it leaves live (`ops/wf-board.plist`) renders to, filled in with the node, checkout, PATH and data directory that the installed file already holds and the job's own home, and when the two texts differ it writes the new file, stops the service with `launchctl bootout`, waits until launchd has let go of it, loads it again with `bootstrap` and judges that as the deploy's restart, for a commit that is already live as well as for a deploy that moves the checkout, because launchd reads a service's arguments only when it loads the service, so `kickstart` restarts the daemon on the arguments launchd already holds, a template change would reach the live daemon only when someone installs the file by hand, and a template merged before the job could replace the file (the job's own code reaches the checkout through a run that does not have it) would stay unapplied until the next merge ([Deploying](../../docs/design.md#4-architecture)), instead of restarting with `kickstart` only or replacing the file only when a deploy's changed paths name the template.

Decision: A deploy that fails after the job began replacing the file goes back to the last healthy commit and writes the old text of the file again, which the job keeps in its pending record from the moment the replacement begins, then stops and loads the service again before the rollback counts as finished, and a commit that is live already and fails only through its file is put back the same way, marked failed and not tried again until the main line has a newer commit, because a daemon that cannot start under the new file is not brought back by the old code alone, and going back must not depend on the new file ([Deploying](../../docs/design.md#4-architecture)), instead of putting back the code and leaving the file.

Decision: An installed file the job cannot read the values from, or a template with a placeholder that no value fills, is not replaced: the run ends as a failure of the job itself, nothing is moved and the architect is told once, because the node and PATH of a machine are the owner's choice and a guess would change what the daemon runs under ([Deploying](../../docs/design.md#4-architecture)), instead of filling the template with the deploy job's own environment.

Rejected:
- Replacing the file only when a deploy's changed paths name the template: rejected because a template that reached the checkout before the job could replace the file would never be installed, and a file lost or edited by hand would stay so.
- Filling the template with the deploy job's own environment: rejected because the job runs under a PATH and a node of its own, so the daemon's would change silently at the first replacement.
- Writing the file and restarting with `kickstart -k`: rejected because `kickstart` restarts the loaded service with the arguments launchd holds and does not read the file.
- Loading the new file as soon as `bootout` returns: rejected because `bootout` returns before a process that shuts down slowly has exited, and `bootstrap` fails with exit status 5 until launchd has let the service go (measured with a throwaway service on the owner's Mac).
- The daemon starting itself again with the flags in its template: rejected because launchd then reports the outer process, which the deploy's judgment of a new process that stays up reads, two processes hold the memory the flags are meant to save, and the template would no longer be the one place a start argument is written.
