Decision: A project is deleted by one tool that only the architect uses and only when the project holds nothing, that is no item, no card or note on its items and no glossary term, the call being refused with the count and first keys of what is left, and the project's own configuration (its repository, its main line, its place in the page order, its name in the project lists of tags and its glossary file, empty by then) goes with it while the commits and log lines that name it as author stay as written, because the board's first priority is that nothing on it is lost or silently changed, so a project with items, cards, notes or terms is moved out of first by the tools that already exist, and a project with none of them is only a line in every list that reads the project list, while the history is read from the board as it was at each commit, so reading it needs no project configured now ([Deleting a project](../../docs/design.md#9-project-responsibility)), instead of deleting a project together with its contents, marking it retired and hiding it, or letting a project delete itself.

Decision: The architect may remove a term from another project's glossary, and a project that a tag is limited to alone is not deleted before the vocabulary is changed, because a retired project cannot write its own glossary, so its terms would keep it on the board for ever, and a tag with no project list applies to every project, so taking the only project out of its list would widen the tag, and the vocabulary changes only when the owner approves it on a card ([Deleting a project](../../docs/design.md#9-project-responsibility)), instead of deleting the terms or the tag together with the project.

Rejected:
- Deleting a project together with its items, cards, notes and terms: rejected because the board would lose what it holds, which breaks the first priority that nothing on it is lost, and other items name those keys.
- A retired mark on the project that hides it from the lists: rejected because every reader of the project list would have to filter, the entry would stay in the data, and the request was to take the project off the board.
- Letting a project delete itself: rejected because its agent could then remove the configuration its own work and credentials depend on.
- Deleting the terms with the project, or a tag that only the project used: rejected because terms are definitions the owner reads and the vocabulary changes only on the owner's approval, so either would be a deletion the refusal exists to prevent.
