Decision: The jump to the next unread change is held on a board of the live board's weight by a lane that runs the real page in jsdom in Node, with the server's answers to a first walk recorded once and replayed to every window, in two layers: exact counts that hold on any machine (no rebuild of the rules, no filter count, at most two draws, the markup written and the elements made held at their measured medians, the answer delays of the baselines set on a virtual clock so that a row around the target that answers in time is measured on a copy of the page that waits 2 seconds for it, the row answering after 300 ms, and a late row may be drawn on its own, and while sessions write, with each write a change event of a real write delivered right after the key, no derivation of the rules from scratch except in a new minute and no count of every item's filters), and the event loop's busy time from the key until the page is quiet, as the page of the commit over the page of its base, quiet and with a write in each press, in interleaved pairs with the twin of the base as the control, red when the 95% interval of the ratio of the paired logs lies wholly on the slower side of 1 and the twin's interval holds 1 within the noise floor measured for that kind of press, otherwise more pairs, then a warning that the run could not decide, because jsdom's time is not a browser's and a hosted runner's speed differs by up to a factor of two between jobs, so no fixed number of seconds is right for every run while the noise of the same page against its own twin is measured in the run itself ([The n-key lane](../../docs/design.md#the-n-key-lane)), instead of a time limit of fixed seconds in a browser.

Rejected:
- A time limit alone: rejected because the time depends on the runner and varies up to a factor of two between jobs.
- A fixed time limit on a pull request (the former median of 0.2 seconds and 90th percentile of 0.3 seconds in the browser, the owner's 0.2 seconds for n being held on the 14900K or by use): rejected because jsdom's time is not a browser's and a fixed number is wrong for some run; the pairs against the base page measure each run's own noise.
- A row that answers 40 ms inside the page's own 100 ms wait: rejected because a browser held up for 40 ms turned the count on slow runners; the 100 ms itself is held by fake-clock tests of the page.
- A fake clock for the page's timers in the browser: rejected because the page's frames, the test's waits for the page to be quiet and the minute timers would all have to follow it, and a fake clock mixed with real network requests stalls; in jsdom the clock stands only for the timers longer than a frame and for the answers a test holds back.
- The time limit on the 14900K only: rejected because only the PM starts runs there, so it cannot guard every pull request.
- The time from the key to the landing instead of the event loop's busy time: rejected because its twin noise at the 90th percentile was 68% against 5.5% for the busy time's median.
- A time layer that only reports and never fails: rejected because a lane that slows down must turn something red or the slowdown goes unnoticed.
- Red only above a minimum size of change (a picked percentage): rejected because the noise differs between machines and a picked threshold means nothing; the interval and the twin decide.
