Decision: The jump to the next unread change is held on a board of the live board's weight by a lane that runs the real page in jsdom in Node, with the server's answers to a first walk recorded once and replayed to every window, in two layers: exact counts that hold on any machine (no rebuild of the rules, no filter count, at most two draws, the markup written and the elements made held at their measured medians, the answer delays of the baselines set on a virtual clock so that a row around the target that answers in time is measured on a copy of the page that waits 2 seconds for it, the row answering after 300 ms, and a late row may be drawn on its own, and while sessions write, with each write a change event of a real write delivered right after the key, no derivation of the rules from scratch except in a new minute, no count of every item's filters, and neither the page's structure nor the lists of stops made again except in a new minute), and the event loop's busy time from the key until the page is quiet, as the page of the commit over the page of its base, quiet and with a write in each press, in interleaved pairs with the twin of the base as the control, each window evaluating a source text of its own, each press after a minor collection of the heap the windows share and the windows opening in a random order with one full collection once they are open and pressing in a random order, both drawn afresh each round with a seed of each run's own, because a press otherwise paid for the collections and compilations the presses of other windows left, and any fixed order turns what the windows before leave, or being the window whose page was built first, into a bias the interval does not see (the twin of an unchanged page read 0.77% slower than the base over 60 runs, a copy of the base in the changed page's place up to 1.5%; [The n-key lane](../../docs/design.md#the-n-key-lane), What a press inherits), red when the 95% interval of the ratio of the paired logs lies wholly on the slower side of 1 and the twin's interval holds 1 within the noise floor measured for that kind of press, and a second run in fresh windows judges the same, otherwise more pairs, then a warning that the run could not decide, because jsdom's time is not a browser's and a hosted runner's speed differs by up to a factor of two between jobs, so no fixed number of seconds is right for every run while the noise of the same page against its own twin is measured in the run itself ([The n-key lane](../../docs/design.md#the-n-key-lane)), instead of a time limit of fixed seconds in a browser.

Rejected:
- A time limit alone: rejected because the time depends on the runner and varies up to a factor of two between jobs.
- A fixed time limit on a pull request (the former median of 0.2 seconds and 90th percentile of 0.3 seconds in the browser, the owner's 0.2 seconds for n being held on the 14900K or by use): rejected because jsdom's time is not a browser's and a fixed number is wrong for some run; the pairs against the base page measure each run's own noise.
- A row that answers 40 ms inside the page's own 100 ms wait: rejected because a browser held up for 40 ms turned the count on slow runners; the 100 ms itself is held by fake-clock tests of the page.
- A fake clock for the page's timers in the browser: rejected because the page's frames, the test's waits for the page to be quiet and the minute timers would all have to follow it, and a fake clock mixed with real network requests stalls; in jsdom the clock stands only for the timers longer than a frame and for the answers a test holds back.
- The time limit on the 14900K only: rejected because only the runner starts runs there, so it cannot guard every pull request.
- The time from the key to the landing instead of the event loop's busy time: rejected because its twin noise at the 90th percentile was 68% against 5.5% for the busy time's median.
- A time layer that only reports and never fails: rejected because a lane that slows down must turn something red or the slowdown goes unnoticed.
- Red only above a minimum size of change (a picked percentage): rejected because the noise differs between machines and a picked threshold means nothing; the interval and the twin decide.
- A rotating order of the windows: rejected because it balances the place in the round but not the window before, and the base came right after the slow witness in three presses of four.
- A fixed cycle of rounds in which each window comes right after each other once: rejected because the effect of a press reaches further than the next one; the base came two presses after the slow witness in two rounds of three and read about 1% slower than its twin over 30 rounds.
- A full garbage collection before each press: rejected because it cost 250 ms a press, 30 seconds a round, where the minor collection removed the bias for about 4 ms.
- The busy time less the collector's pauses: rejected because identical windows still differed by up to 1% and the page's own collections are part of its cost.
- A single-threaded V8: rejected because it doubled the noise per pair and made identical windows differ by 1 to 4%.
- The windows opened in the same order every round: rejected because the window opened first read about 1% slower while writing, every count of its work the same as the others'.
- More pairs spread over parallel jobs and pooled, so that a page 2% slower is red every time: rejected because it needs about eight jobs a phase and a job that pools them, against the full CI's minute, and leaves the rate of false reds as it is.
- A 99% interval for the verdict: rejected because the engineering standards judge a regression by the 95% interval, and it would report a page 2% slower in about one run of five.
- Searching further for the residual bias of the quiet phase (a copy of the base about 0.6% slower than the base): rejected for now because each source took a round of hosted runs to find, and confirming a red in a second run keeps it from reddening a page the same as its base.
