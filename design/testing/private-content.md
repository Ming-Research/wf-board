Decision: A private-content check, a CI check that turns red when the change adds private data to the public repository, runs on every push to any branch and on pull requests, also when a title, body or base is edited, reads only what the change adds (added lines, paths, commit messages, the pull request's title and body, taken from the event file), matches kinds of private data (private network addresses, home directories, SSH keys, private key blocks, token formats, quoted secret literals, paths under the home directory with a word for a secret in them, links to the old board page, scratch directories, backup and environment files) and never a list of the owner's real values, and prints the rule and the place and never the matched text, because what is pushed to a public repository is public at once so the check can only report after the push, a list of real values kept in the workflow would sit in the repository and one kept in a secret could not be shown in the log, and the log of a public repository is public ([Private content check](../../docs/design.md#private-content-check)), instead of a secret list of real values or printing the match.

Rejected:
- A secret list of real values for exact matches: rejected because it needs a secret kept current and nothing has needed it.
- Ignore-file entries for working directories: rejected because the list never ends, and the check catches the path wherever it sits.
- Reading a pull request's title and body from environment variables: rejected because the runner prints them.
