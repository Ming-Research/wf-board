Decision: The last job of the full CI starts with the run and not after the other jobs, waits until every other job has ended (a look at the Actions API every 2 seconds while more than 4 jobs are open, every second after that), writes the status `full-ci` itself on a run started by hand (success when every job succeeded or was skipped and the judged time is not red) and puts into the run's summary the seconds from the start of the run to the status, the judged time, the time of each job and a table of the test shards that names a shard over 1.5 times the mean of the others, with the judged time yellow above 50 seconds and red above 60, and a red one fails the status and the job, because a lane that slows down must turn something red or the minute for a pull request's checks is lost unnoticed, two runs of one configuration differed by 13% so a typical 50 seconds leaves the line 20% above, and a job that needs the others started 2 to 3 seconds after the last of them and set itself up after that, so that the status came 6 to 10 seconds after the last check where a job that waited wrote it 1 to 2 seconds after (8 samples each) ([The time gate](../../docs/design.md#the-time-gate)), instead of limits on each job's own time alone, no gate, a gate that only reports, or a job that needs the others.

Decision: No job of the full CI may use `needs`, because a job is listed in the run only once the jobs it needs have ended, and the job that waits would not wait for it. The jobs it waits for have a timeout of 10 minutes each, each step of the job itself one (5 minutes, the script's 15) and the job none, because GitHub cancels a job for its timeout without running another step, so a timeout on the job leaves the status pending, while a step that times out fails and the step after it, which runs when a step failed and the script wrote nothing, writes the failure; a job that hangs is cancelled before the script's step ends unless it started more than about 5 minutes late, since a job's timeout counts from when it starts to run, and then the script writes a failure naming the job, else the step after the script's writes one that does not. The browser tests are a workflow of their own and not in this run, so the total is the script tests' and a red that never clears cannot happen.

Decision: The time that is judged leaves out the wait for a runner that a job had beyond the quickest job of the run: each job's end is moved back by the seconds its wait for a runner (from its creation to the start of its first step) exceeded the quickest job's, the job that reads counting by its start, the latest of these is when the status could have been written had every job been served as soon as the quickest one, and the delay from the last end to the status is added, while the total and the part of it that was waiting are written in the status description and the run's summary, because the wait belongs to the runner pool and not to the change, and a job that is slow itself still ends late and stays counted: of the 52 runs started by hand with the script that waits (10-19, hosted runners), 8 ended over 60 seconds by the total, 5 of them only because a job started 21 to 45 seconds late, which come to 46 to 55 seconds by the rule, and the 3 whose jobs ran slow stayed at 61 to 71; the waits came from the organization's jobs running at once reaching the 60 its plan allows (9 of 143 runs) and from single jobs given a runner late (5 of the other 134), so no change to the CI prevents them; the run's own quickest job stands for the shortest wait, so that no number is picked ([The time gate](../../docs/design.md#the-time-gate)), instead of the total with the wait counted, the total with the wait only written beside it, the longest job's own time with no wait counted, a run started again when it is red for the wait, or fewer jobs in a run. A run in which every job waited alike has no quicker job to compare with and keeps that wait.

Decision: A push to the main line runs the same job in the mode `record`, which writes the summary and no status and neither fails the script nor, through `continue-on-error`, the job, because every merge then leaves the table of waits on the main line where the trend of the runner pool can be read, and a report must not turn the main line red, since the checks of a push are what the deploy reads, instead of the job on runs started by hand alone, where the waits would be known only for the runs of the pull requests.

Rejected:
- Limits on each job's own time alone: rejected because the target is the minute from the start of the run to the status, which holds the start of every job and the delay after the last, and a limit for each of 28 jobs would need 28 numbers that say nothing of that sum.
- A table of times with no limit: rejected because nothing turns red when the run slows down, which was the state before the gate.
- A job that needs the others, with a lean step: rejected because it still starts 2 to 3 seconds after the last check and the status came 5 to 6 seconds after it, against 1 to 2 for the job that waits.
- The last check job writing the status: rejected because two jobs that end at the same moment each find the other still running, nobody writes, and the status stays pending.
- A timeout on the job that writes the status: rejected because a job cancelled for its timeout runs no step after it, so neither the script nor the step that writes a failure would run and the status would stay pending.
- The total with the wait for a runner counted, as before: rejected because 5 of the 52 runs started by hand were red for the wait alone, each costing the engineer a second run and another minute, while every job's own time was inside the line.
- The total with the wait only written beside it: rejected because the status still fails, and a pull request does not merge on a red status, so the same 5 runs are run again.
- The longest job's own time with no wait counted at all: rejected because it moves the line up about 4 seconds (median 48 against 52 of the total, 52 runs), so that the 50 and 60 no longer mean what was set, and a run of 61 seconds whose jobs ran slow reads 58 and passes.
- A run started again when it is red for the wait: rejected because the engineer waits twice, and the second run's 28 jobs queue for the same runners, which lengthens the queue when the organization's job limit is the cause.
- Fewer jobs in a run so that three runs fit under the limit of 60: rejected because it cures only the waits the limit causes and not a single job given a runner late, and the 20 shards are what keep the run near 50 seconds ([Sharding the script tests](../../docs/design.md#sharding-the-script-tests)).
- The job on runs started by hand alone: rejected because only the runs of pull requests would then show waits, and a main line push is the one run per merge that is not crowded by an engineer's repeated starts.
